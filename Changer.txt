3. Pre-flight checklist, Phase-2-specific
3.1 — Confirm gtsam actually installed, not just attempted.

python3 -c "import gtsam; print(gtsam.__file__)"
gtsam's Python bindings are a compiled wheel with real binary
dependencies (Eigen, Boost in some builds). A pip install gtsam that
appears to succeed but was actually served from a cache or partial
download can produce confusing ImportErrors only when a specific
submodule is touched (e.g. gtsam.noiseModel.mEstimator), not at the top-
level import gtsam. Test the actual symbols this code uses:

import gtsam
from gtsam import Cal3_S2Stereo, StereoPoint2, GenericStereoFactor3D, GenericProjectionFactorCal3_S2
from gtsam.symbol_shorthand import X, L

4. Symptom → diagnosis → fix (GTSAM-specific)
4.1 — ImportError or ModuleNotFoundError: No module named 'gtsam'
Not a code bug. Either pip install gtsam wasn't run, or it silently
failed (check pip list | grep -i gtsam). If you don't want to debug a
gtsam install right now, set backend: "scipy" in config and proceed —
Phase 1's fixes are backend-independent, you don't need GTSAM working to
test Phase 1's map-lifecycle fix on hardware.

4.2 — RuntimeError: An inference algorithm was called with inconsistent arguments
This exact message covers two different root causes in this codebase
(see bundle_adjust_gtsam.py's docstring, Bugs 1 and 3) — both were found
and fixed, but if you see this message again on real hardware data, it
means a THIRD variant of the same class of bug exists that the synthetic
tests didn't reproduce. Useful things to capture before reporting:

# right before the crash, dump exactly what's inconsistent:
print("free kfs:", [kf.id for kf in free_kfs])
print("fixed kfs:", [kf.id for kf in fixed_kfs])
print("points:", len(points), "total observations touched:", n_obs)
Real sensor data has messier edge cases than synthetic sequences —
duplicate keyframe insertion during a race between tracking and local
mapping, a map point erased mid-BA-call, etc. If this fires, it's a real
finding, not noise — send me the three print lines above plus the
surrounding [TRACK]/[RGBD] log context.

4.3 — [BA-GTSAM] cost goes to ~0 but the trajectory looks visibly wrong
This is exactly Bug 2 from Phase 2's own verification — the gauge/scale
ambiguity signature. It should be structurally prevented now (every BA
call either has a real fixed anchor or the explicit fallback prior), but
if you see a suspiciously perfect cost alongside an implausible trajectory
jump, check:

[BA-GTSAM] N free + M fixed kfs, ...
If M fixed kfs = 0 on a call where the map clearly has more keyframes
than the window, that's the bug resurfacing — the fixed-keyframe detection
logic didn't find an anchor when one should exist. Report the map size at
that point (n_keyframes_alive from metrics.map_health()) alongside the
window setting.

4.4 — GTSAM backend is noticeably slower than scipy, not faster
Expected in small-map regimes, not a regression. Phase 2's own
measurement: on a healthy, properly-culled 60-frame map (Phase 1 working
as intended), a single GTSAM BA call took ~75-80ms, comparable to scipy's
baseline — GTSAM's real advantage (marginalizing landmarks so cost scales
with pose count, not pose+landmark count) shows up as the number of FIXED
keyframes grows, which is exactly the scenario Phase 1's culling fix is
designed to prevent from happening uncontrolled. In other words: if
Phase 1 is working, you may not see a dramatic GTSAM speed advantage on
short test clips, and that's consistent with everything measured so far,
not a sign something's wrong. The comparison that WOULD show a difference
needs a much longer, more keyframe-dense recording than a 10-30s D435i
clip — not worth engineering a hardware test around Phase 2 alone.

4.5 — Poses "jump" specifically at the moment BA switches between scipy and gtsam mid-run
Should not happen — the backend is selected once at SLAMSystem
construction from config, not per-call. If you see this, check you're not
accidentally constructing two different SLAMSystem instances (e.g., one
for a warm-up pass, one for the real run) with different configs loaded.

4.6 — Points visibly drift or the map looks warped after a GTSAM BA call, but no crash and no gates fail
The synthetic gates test bounded, well-behaved input. Real sensor depth
noise is heavier-tailed (holes, flying pixels at depth discontinuities,
occasional gross outliers near object edges). The Huber robust kernel
(huber_f_scale in config) is meant to down-weight these, but if a
specific keyframe has an unusually high fraction of bad depth (e.g.
pointed at a reflective/transparent surface), even Huber can't fully
compensate. This is a real, expected RGB-D limitation, not a GTSAM
integration bug — but if it's happening frequently, it's worth logging
which observations are stereo-factor vs mono-fallback (n_obs_stereo vsn_obs - n_obs_stereo in the [BA-GTSAM] line) since a high mono-
fallback fraction means a lot of points are being optimized WITHOUT the
depth constraint that fixes Bug 2 — i.e., check whether your D435i's
depth-valid fraction on the affected keyframes is unusually low.
