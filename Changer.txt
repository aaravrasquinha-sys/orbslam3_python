Airtel AMF311 Dongle Recovery Runbook (HP Z440, Ubuntu)
Oct 27, 2026 · @Aarav
How to use this runbook
Go through the phases in order. Each phase ends with a PASS → go to or FAIL → go to line, so you always know where to jump next. The most likely root cause is that NetworkManager's old profile no longer matches the dongle after the USB controller hung. Phase 5 is the permanent fix; Phases 1–4 make sure the dongle reaches that point.
Your setup: no second internet connection, no second device and no USB hub. So everything here uses only what is already installed on the Z440, nothing needs the internet, and each risky step says what to do if your keyboard stops responding. Write the values you find in the table below on paper, since you can't look anything up elsewhere.
Golden rules
• Change one thing at a time, then test. Never run two fixes together.
• Keep a second terminal open running sudo dmesg -w. It shows live what the kernel sees when you plug or unplug the dongle.
• Wait 20–30 seconds after plugging in before deciding something failed. The dongle has to boot and register on 4G.
• Plug the dongle directly into the Z440, with no hub and no extension cable, until everything works.
• In every command, replace VVVV:PPPP with your dongle's USB ID and IFACE with its interface name. Fill both in the table below once you find them.

Phase 0: Prepare (do this first)
Everything in this runbook works offline. Spend five minutes here so you know which tools you have and what your escape routes are before you change anything.
0.1 Keep this runbook readable. The Z440 can't open it until its internet is back, so keep it open on the device you're reading it on now. Also export it to PDF or print it, so it survives a flat battery.
0.2 Check which tools are already on the Z440. You can't install anything, so you need to know what you have:
for c in usb_modeswitch eject nmcli lsusb dhclient python3 nano; do printf '%-16s' $c; command -v $c || echo MISSING; done
dpkg -l | grep -E 'usb-modeswitch|linux-modules-extra|network-manager' | awk '{print $1, $2, $3}'
ls /boot/vmlinuz*
Write down anything marked MISSING. nmcli and lsusb ship with Ubuntu Desktop and are needed from Phase 1 onward. usb_modeswitch and eject matter only if the dongle is stuck in CD-ROM mode (Phase 2). More than one vmlinuz file means an older kernel is installed, which is your offline fallback in Phase 3.3.
0.3 Know your two escape routes before you start. With no second device, these are how you recover from a hang: the full power drain (Phase 1.7) and booting the older kernel from the GRUB menu (Phase 3.3). Read both now. Save any open work before every reboot or USB reset.
0.4 Save a snapshot of the current state so you can compare later:
mkdir -p ~/dongle-debug && cd ~/dongle-debug
nmcli connection show > nm-connections-before.txt
ip addr > ip-addr-before.txt; ip route > ip-route-before.txt
ls /etc/netplan/ > netplan-files.txt; sudo cat /etc/netplan/*.yaml > netplan-before.txt
ls -lt /boot/vmlinuz* > kernels.txt; uname -r >> kernels.txt
PASS → go to Phase 1.
Phase 1: Does the Z440 see the dongle on USB?
Goal: the dongle appears in lsusb. Nothing else can work until it does.
1.1 Check that the dongle itself is alive. Power it on. Look for its signal/network light, or check from your phone whether its WiFi name is visible. If the dongle shows no lights or no WiFi on any power source (a phone charger works too), the dongle is the problem, not Ubuntu. Contact Airtel.
1.2 Plug it in and look
sudo dmesg -w          # terminal 1: leave this running
lsusb                  # terminal 2: run 15 s after plugging in
lsusb -t               # shows which driver grabbed each device
PASS (a new line appears in lsusb; note its ID VVVV:PPPP) → go to Phase 2.
FAIL (no new line in lsusb) → work through 1.3 to 1.8 in order, testing after each one.
1.3 Read what dmesg printed when you plugged in
• Nothing printed at all → the port or controller is dead or hung. Go to 1.4.
• device descriptor read/64, error -71 or error -110 or unable to enumerate USB device → bad contact, cable, or not enough power. Go to 1.4 and 1.5.
• over-current condition → that port has shut itself off. Go to 1.6 (full power drain).
1.4 Try other ports. Use the rear ports first, as they connect straight to the motherboard. If the Z440 has rear USB 2.0 ports (black, not blue), try those too; some 4G dongles behave better on USB 2.0. You have no hub, which is ideal: keep it that way, and don't use an extension cable either. Move the keyboard and mouse to the front ports so the rear ports stay free for the dongle and for testing.
1.5 Try another cable or extension if the dongle connects through one. Cheap extensions often cause error -71.
1.6 Reset the USB controller without rebooting. This briefly disconnects every USB device, including your keyboard and mouse, for about 5 seconds.
lspci | grep -i usb        # note the address at the start, e.g. 00:14.0
sudo sh -c 'echo -n 0000:00:14.0 > /sys/bus/pci/drivers/xhci_hcd/unbind; sleep 5; echo -n 0000:00:14.0 > /sys/bus/pci/drivers/xhci_hcd/bind'
Run the second line exactly as one line, so the bind always follows the unbind. Replace 00:14.0 with your address. If lspci shows more than one USB controller, try each.
Risk with no second device: if your keyboard and mouse are USB, they go dead during the reset. Save your work first. They normally come back on their own when the bind command runs. If they are still dead after 15 seconds, hold the power button for 5 seconds to force off, then do the power drain from step 2 of 1.7.
1.7 Full power drain (what worked for you this morning)
1. Shut down Ubuntu normally (sudo poweroff).
2. Remove the power cable from the back of the Z440.
3. Hold the power button for 30 seconds.
4. Wait 1 minute, reconnect power, boot.
5. Plug in the dongle after you have logged in.
1.8 Check the BIOS if none of the ports work for anything. Press F10 at boot to enter HP BIOS setup. In the advanced / port options, make sure the USB ports are enabled and nothing is set to disabled.
If lsusb still shows nothing after 1.8 and the dongle's own Wi-Fi name shows up on your phone (so the dongle itself is alive), the Z440's USB controller may be damaged. A cheap PCIe USB card is the workaround.
Why this happened: after 3 days of continuous running, the USB controller or port most likely went into a hung or power-saving state. Phase 6 makes that much less likely to happen again.

Phase 3
2.1 Switch it out of CD-ROM mode by hand
Try these one at a time. After each, wait 15 seconds and run ip -br link to see if an enx… / usb0 interface appeared.
Check which tool you have (Phase 0.2). usb_modeswitch and eject are usually preinstalled on Ubuntu Desktop; use whichever is present. If neither is, use the Python fallback just below the PASS and FAIL lines.
sudo usb_modeswitch -v 0xVVVV -p 0xPPPP -K     # standard eject
sudo usb_modeswitch -v 0xVVVV -p 0xPPPP -X     # alternative eject
sudo eject /dev/sr0                            # plain eject of the fake CD
Note: after a successful switch the dongle reconnects with a new USB ID. Run lsusb again and write down both IDs (before and after).
PASS (a network interface appears) → do 2.2 to make it permanent, then go to Phase 3.
FAIL → unplug the dongle for 30 seconds, plug it into a different port, and try 2.1 again. If it still fails, the dongle may simply need more time: some dongles switch by themselves after 30–60 seconds. Wait a full minute before giving up.
No usb_modeswitch or eject installed? You can't install them offline, but python3 can send the same eject request to the fake CD:
sudo python3 -c "import os,fcntl; fd=os.open('/dev/sr0', os.O_RDONLY|os.O_NONBLOCK); fcntl.ioctl(fd, 0x5309)"
If /dev/sr0 doesn't exist, find the fake CD with lsblk (a small device of type rom) and use that name. The dongle worked for 2 months, so it was switching modes on its own before. The usual reason it stops is a missing driver, so check lsusb -t for a bound driver first and read Phase 3.
2.2 Make the switch automatic every time
Use whichever command worked in 2.1 (-K or -X). Use the before-switch ID here:
echo 'ACTION=="add", SUBSYSTEM=="usb", ATTR{idVendor}=="VVVV", ATTR{idProduct}=="PPPP", RUN+="/usr/sbin/usb_modeswitch -v 0xVVVV -p 0xPPPP -K"' | sudo tee /etc/udev/rules.d/40-airtel-modeswitch.rules
sudo udevadm control --reload-rules
In the rule, write VVVV and PPPP without 0x, lowercase, exactly as lsusb shows them. Keep the 0x in the command part.
2.3 Serial modem mode (only if you saw ttyUSB)
This means the dongle is acting as an old-style modem, not as a network card. First try 2.1, since many dongles move from this mode to network mode with a mode switch. If you still only get ttyUSB ports:
sudo systemctl enable --now ModemManager
mmcli -L                           # should list a modem
sudo nmcli connection add type gsm ifname '*' con-name Airtel-GSM apn airtelgprs.com connection.autoconnect yes
Then skip Phase 5 (that phase is for network mode) and go to Phase 6.
2.4 It worked for 2 months, so why would the mode change? The usual reasons are a kernel or usb-modeswitch update during the 3-day run, or the dongle being plugged in before the system finished booting. Phase 3 checks for an update.
Phase 3: Is the kernel driver present?
Ubuntu may have installed a new kernel automatically during the 3-day run. If the network driver is missing from that new kernel, the dongle is seen on USB but never becomes a network interface.
3.1 Check for a recent kernel update
uname -r                                   # kernel running now
ls -lt /boot/vmlinuz*                      # installed kernels, newest first
grep -E 'linux-image|linux-modules' /var/log/apt/history.log | tail
sudo tail -30 /var/log/unattended-upgrades/unattended-upgrades.log
If a linux-image was installed in the last few days, keep that in mind for 3.3.
3.2 Check the drivers exist and load them
modinfo rndis_host cdc_ether cdc_ncm usbnet | grep filename
sudo modprobe rndis_host; sudo modprobe cdc_ether; sudo modprobe cdc_ncm
lsmod | grep -E 'rndis|cdc|usbnet'
• All filename lines print → the drivers exist. Unplug and replug the dongle, then check ip -br link. A new enx…/usb0 interface → PASS, go to Phase 4.
• modinfo: ERROR: Module … not found → the driver is missing. Go to 3.3.
3.3 Missing driver: fixes that work offline
1. Boot the older kernel (the main fix, no internet needed). Reboot. Right after the HP logo, hold Shift (BIOS boot) or tap Esc (UEFI boot) to get the GRUB menu. Choose Advanced options for Ubuntu, then the previous kernel (not "recovery mode"). After login, run uname -r to confirm it is the older one, then replug the dongle and check ip -br link.
2. If the dongle works on the older kernel, the new kernel is missing its extra modules. You now have internet through the dongle, so run ls /boot/vmlinuz* to see the new version, then sudo apt update && sudo apt install linux-modules-extra-<new-version> and reboot into the new kernel to test.
3. Until that's done, make the older kernel the default so a reboot doesn't strand you. Run sudo nano /etc/default/grub, set GRUB_DEFAULT="1>2", then sudo update-grub. This means Advanced options, then its third entry (the order is newest kernel, its recovery mode, previous kernel); check that against what you saw in the menu. Set it back to GRUB_DEFAULT=0 once step 2 works.
4. If the older kernel doesn't help either, the driver isn't the problem. Go back to Phase 1 (power drain) and Phase 2 (mode).
5. Force the module to bind (rare), if modinfo works but no interface appears: echo VVVV PPPP | sudo tee /sys/bus/usb/drivers/rndis_host/new_id.
3.4 Optional: stop surprise kernel updates mid-run. Unattended upgrades install security updates automatically. If you'd rather choose when kernels change, disable automatic installs with sudo dpkg-reconfigure unattended-upgrades and answer No. Remember to update manually from time to time.

4.1 Is the dongle unmanaged? Look at the IFACE line in nmcli device status.
• connected → it's already working. Go to Phase 5 anyway, to make it permanent.
• disconnected → NetworkManager sees it but has no matching profile. Go to Phase 5, Option A.
• connecting (getting IP configuration) for a long time → the dongle isn't answering DHCP yet. Wait 60 seconds; if still stuck, see the troubleshooting matrix.
• unmanaged → go to 4.2.
4.2 Fix unmanaged
sudo nmcli device set IFACE managed yes
grep -r unmanaged /etc/NetworkManager/ /usr/lib/NetworkManager/conf.d/ 2>/dev/null
If grep shows a file containing unmanaged-devices= or a file named 10-globally-managed-devices.conf, NetworkManager is set to ignore ethernet devices. Fix it by overriding:
sudo touch /etc/NetworkManager/conf.d/10-globally-managed-devices.conf
sudo systemctl restart NetworkManager
An empty file in /etc with the same name overrides the one in /usr/lib. If the unmanaged setting came from a file in /etc/NetworkManager/ instead, open it with sudo nano <file> and delete or comment out (#) that line, then restart NetworkManager.
Also make sure netplan hands control to NetworkManager. The file in /etc/netplan/ should contain:
network:
  version: 2
  renderer: NetworkManager
If you change it: sudo netplan generate && sudo netplan apply.
PASS (state is no longer unmanaged) → Phase 5, Option A.
4.3 Both managers active. On a Desktop install, keep NetworkManager. Set renderer: NetworkManager as in 4.2, run sudo netplan apply, then reboot. Then go to Phase 5, Option A.
Phase 5: The permanent fix (auto-connect on every plug-in)
This is the core fix. The new profile matches the dongle by its driver, so it keeps working even if the interface name or MAC address changes after a reset.
Option A: NetworkManager (Ubuntu Desktop)
5.1 Clear out this morning's manual setup
sudo ip addr flush dev IFACE
sudo ip route flush dev IFACE
5.2 Remove old, stale profiles
nmcli -f NAME,UUID,TYPE,DEVICE connection show
Delete any wired/ethernet profile that belonged to the dongle (often Wired connection 1, Wired connection 2, or one named after the dongle). Do not delete your Wi-Fi or the profile for the Z440's built-in ethernet port if you use it.
sudo nmcli connection delete "Wired connection 1"
If several have the same name, delete by UUID: sudo nmcli connection delete <UUID>.
5.3 Create the driver-matched profile
sudo nmcli connection add type ethernet con-name Airtel-4G \
  match.driver "rndis_host cdc_ether cdc_ncm" \
  ipv4.method auto ipv4.route-metric 50 ipv4.dhcp-timeout 90 \
  ipv6.method auto ipv6.may-fail yes \
  connection.autoconnect yes connection.autoconnect-priority 50 \
  connection.autoconnect-retries 0
What the settings do:
• match.driver → the profile applies to any interface using these drivers, whatever its name or MAC.
• ipv4.route-metric 50 → the dongle wins over other wired connections for internet.
• ipv4.dhcp-timeout 90 → gives the dongle time to register on 4G before NetworkManager gives up.
• connection.autoconnect-retries 0 → keep retrying forever instead of giving up after 4 failures.
If the command fails with an error about match.driver (very old NetworkManager), use this instead:
sudo nmcli connection add type ethernet con-name Airtel-4G ifname IFACE \
  ipv4.method auto ipv4.dhcp-timeout 90 connection.autoconnect yes connection.autoconnect-retries 0
This version is tied to the interface name, so it may break again if the name changes.
5.4 Check the profile is not tied to a MAC address
nmcli connection show Airtel-4G | grep -iE 'mac-address|interface-name|match'
ethernet.mac-address and connection.interface-name should be empty (--), and match.driver should show the three drivers. If a MAC is set: sudo nmcli connection modify Airtel-4G ethernet.mac-address "".
5.5 Bring it up
sudo nmcli connection up Airtel-4G
ip -br addr show IFACE
ip route
ping -c3 8.8.8.8
ping -c3 google.com
• All pings work → PASS, go to Phase 6.
• 8.8.8.8 works but google.com fails → DNS problem. Run sudo nmcli connection modify Airtel-4G ipv4.dns "8.8.8.8 1.1.1.1" && sudo nmcli connection up Airtel-4G.
• nmcli connection up fails with a timeout → see the troubleshooting matrix, row "IP configuration could not be reserved".
• Error: no device found → the profile doesn't match the driver. Check lsusb -t shows one of the three drivers; add the actual driver name to match.driver.
Option B: systemd-networkd (Ubuntu Server)
Create a netplan file that matches the dongle by driver:
sudo nano /etc/netplan/60-airtel.yaml
Paste this (spaces matter, no tabs):
network:
  version: 2
  ethernets:
    airtel-rndis:
      match:
        driver: rndis_host
      dhcp4: true
      optional: true
    airtel-ecm:
      match:
        driver: cdc_ether
      dhcp4: true
      optional: true
    airtel-ncm:
      match:
        driver: cdc_ncm
      dhcp4: true
      optional: true
Then:
sudo chmod 600 /etc/netplan/60-airtel.yaml
sudo netplan generate        # no output = no syntax errors
sudo netplan apply
networkctl status IFACE
optional: true stops the boot from waiting 2 minutes when the dongle isn't plugged in. If netplan generate prints an error, it names the line; usually an indentation mistake.
PASS → go to Phase 6.
Phase 6: Stop it breaking again on long runs
These steps target the real trigger: the USB link going to sleep or hanging during multi-day runs.
6.1 Keep the dongle's USB port always powered
Use the ID the dongle has in network mode (after any mode switch):
echo 'ACTION=="add", SUBSYSTEM=="usb", ATTR{idVendor}=="VVVV", ATTR{idProduct}=="PPPP", TEST=="power/control", ATTR{power/control}="on"' | sudo tee /etc/udev/rules.d/50-airtel-power.rules
sudo udevadm control --reload-rules
Unplug and replug, then check it took effect:
for d in /sys/bus/usb/devices/*; do [ "$(cat $d/idVendor 2>/dev/null)" = "VVVV" ] && echo "$d: $(cat $d/power/control)"; done
It should print on. If it prints auto, the rule didn't match; check the ID is lowercase and has no 0x.
6.2 Stronger option: turn off USB autosuspend for the whole system
Use this if the dongle still drops out after 6.1. It costs a little idle power, which doesn't matter on a workstation.
sudo nano /etc/default/grub
Find the line GRUB_CMDLINE_LINUX_DEFAULT="quiet splash" and add usbcore.autosuspend=-1 inside the quotes:
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash usbcore.autosuspend=-1"
Then sudo update-grub and reboot. Check with cat /sys/module/usbcore/parameters/autosuspend; it should print -1.
If TLP is installed (which tlp), it can override this. Add the dongle ID to USB_DENYLIST="VVVV:PPPP" in /etc/tlp.conf and run sudo tlp start.
6.3 Optional: a watchdog that repairs the connection by itself
Useful because you leave jobs running for days. Every 5 minutes it checks for internet. If there is none, it restarts the connection; if that fails, it resets the dongle's USB link (equivalent to unplugging and replugging).
Create the script:
sudo nano /usr/local/bin/airtel-watchdog.sh
#!/bin/bash
# Airtel dongle watchdog: replace VVVV with your vendor ID (lowercase, no 0x)
VENDOR="VVVV"
ping -c 3 -W 3 8.8.8.8 >/dev/null 2>&1 && exit 0
logger "airtel-watchdog: no internet, restarting Airtel-4G"
nmcli connection up Airtel-4G >/dev/null 2>&1 && sleep 10 && ping -c 2 -W 3 8.8.8.8 >/dev/null 2>&1 && exit 0
for d in /sys/bus/usb/devices/*; do
  if [ "$(cat "$d/idVendor" 2>/dev/null)" = "$VENDOR" ]; then
    logger "airtel-watchdog: resetting USB device $d"
    echo 0 > "$d/authorized"; sleep 5; echo 1 > "$d/authorized"
  fi
done
Create the service and timer:
sudo chmod +x /usr/local/bin/airtel-watchdog.sh
printf '[Unit]\nDescription=Airtel dongle watchdog\n\n[Service]\nType=oneshot\nExecStart=/usr/local/bin/airtel-watchdog.sh\n' | sudo tee /etc/systemd/system/airtel-watchdog.service
printf '[Unit]\nDescription=Run Airtel watchdog every 5 min\n\n[Timer]\nOnBootSec=3min\nOnUnitActiveSec=5min\n\n[Install]\nWantedBy=timers.target\n' | sudo tee /etc/systemd/system/airtel-watchdog.timer
sudo systemctl daemon-reload
sudo systemctl enable --now airtel-watchdog.timer
Check it's scheduled with systemctl list-timers | grep airtel, and see what it did with journalctl -t airtel-watchdog.
Caveats: if Airtel's 4G service itself is down, the watchdog will keep resetting the dongle every 5 minutes, which is harmless. If the USB controller itself hangs (as in Phase 1), only a power drain fixes it; the watchdog can't.
If you're on Option B (systemd-networkd), replace the nmcli connection up Airtel-4G line with networkctl reconfigure IFACE.
6.4 Physical tips
• Use a rear port and leave the dongle there permanently.
• Keep the dongle away from the hot exhaust at the back of the Z440 if possible (with no hub or extension available, a front port is the alternative, but test it first). Overheated dongles drop their connection.
• Plug the dongle in after the desktop has finished loading if you notice it fails right after boot.
Phase 7: Get SSH to the Jetson Orin Nano working
The Z440 (over USB) and the Jetson (over Wi-Fi) both need addresses from the dongle on the same subnet. "No route to host" this morning most likely came from the manual setup giving the Z440 a wrong address or route. Only start this phase once Phase 5 passes.
7.0 One keyboard, one monitor, no second computer. Finish Phases 1 to 6 on the Z440 first. For the Jetson steps, move the keyboard (and the monitor cable, or switch the monitor's input) to the Jetson, do those steps, then move them back. The Z440 keeps running meanwhile, so your jobs are not affected.
To find the Jetson's IP without touching the Jetson, from the Z440 (none of this needs internet):
• Open the dongle's admin page in a browser: http://<gateway>, where the gateway is the address after default via in ip route. Its connected-devices or DHCP-clients list shows the Jetson's name and IP. The login is usually printed on the dongle's label.
• Or ping every address on the dongle's network, then read the neighbour table (use your own first three numbers):
for i in $(seq 1 254); do ping -c1 -W1 192.168.1.$i >/dev/null 2>&1 & done; wait
ip neigh | grep -v FAILED
• Or try its name: ping <jetson-hostname>.local.
7.1 Is the dongle's Wi-Fi visible to the Jetson? On the Jetson (monitor + keyboard, or check from your phone):
nmcli device wifi rescan; sleep 5; nmcli device wifi list
• SSID listed → go to 7.2.
• SSID not listed (also not on your phone) → the dongle's Wi-Fi is off. Unplug the dongle for 30 seconds and replug it. Some dongles turn Wi-Fi off after an idle timer or a USB-mode change; open the dongle's admin page (the gateway IP from ip route, typically 192.168.0.1 or 192.168.1.1) and check the Wi-Fi is enabled and any "Wi-Fi sleep" option is off.
• SSID listed, but the Jetson won't join → nmcli connection up "<SSID>" on the Jetson and read the error. A wrong password means the saved one changed; re-enter it with nmcli device wifi connect "<SSID>" password "<password>".

7.3 Same subnet but SSH still fails
ping -c3 <jetson-ip>
ip neigh | grep <jetson-ip>
• Ping works, SSH doesn't → SSH isn't running on the Jetson: sudo systemctl enable --now ssh there.
• Ping fails, ip neigh shows FAILED or INCOMPLETE → the Jetson isn't answering on Wi-Fi. The most common cause is Wi-Fi power saving on the Jetson. Fix it permanently on the Jetson: sudo nmcli connection modify "<SSID>" 802-11-wireless.powersave 2 then sudo nmcli connection up "<SSID>".
• Ping fails to every Wi-Fi device (try your phone's IP too) → the dongle may have client isolation / AP isolation on. Turn it off in the dongle's admin page under Wi-Fi settings.
• ip route shows extra odd routes (e.g. a second default line or a route to the Jetson's subnet via another interface) → leftovers from this morning: sudo ip route flush dev IFACE, then sudo nmcli connection up Airtel-4G, or simply reboot.
7.4 Different subnets
First redo Phase 5.1 and 5.5 to remove any manual address. If the subnets still differ after the Z440 gets its address by DHCP, the dongle keeps USB and Wi-Fi clients apart. Then you have two options:
1. Direct cable (most reliable): connect the Jetson's ethernet port to the Z440's built-in ethernet port. On the Z440, set that port to "Shared to other computers" (sudo nmcli connection add type ethernet ifname <z440-eth> con-name jetson-link ipv4.method shared) and DHCP on the Jetson. The Jetson then gets a 10.42.0.x address and internet through the Z440.
2. Z440 joins the dongle's Wi-Fi instead of USB, if the Z440 has a Wi-Fi adapter.
7.5 Stop the Jetson's IP from changing
Pick one:
• Use its name, not its IP (easiest): make sure avahi-daemon is running on both (sudo systemctl enable --now avahi-daemon), then ssh user@<jetson-hostname>.local. Find the hostname by running hostname on the Jetson.
• DHCP reservation: in the dongle's admin page, look for a DHCP / reserved IP setting and bind the Jetson's MAC address to a fixed IP.
• Static IP on the Jetson: pick an address high in the range so DHCP is unlikely to hand it out, e.g. .200. Use your real subnet and gateway:
sudo nmcli connection modify "<SSID>" ipv4.method manual ipv4.addresses 192.168.1.200/24 ipv4.gateway 192.168.1.1 ipv4.dns "192.168.1.1 8.8.8.8"
sudo nmcli connection up "<SSID>"
Do the static IP on the Jetson with a monitor and keyboard attached, since a mistake will cut your SSH session.
7.6 Offline fallbacks for the Jetson link
• Direct cable (best fallback, needs no dongle). Run an ethernet cable from the Jetson's ethernet port to the Z440's built-in ethernet port and follow option 1 in 7.4. Find the Jetson's address with cat /var/lib/NetworkManager/dnsmasq-<z440-eth>.leases. As a bonus, the Jetson then gets internet through the Z440 whenever the dongle is up.
• Names (.local) need avahi-daemon already installed. Check with systemctl status avahi-daemon. If it says the unit isn't found, it isn't installed and you can't add it offline: use a DHCP reservation or the static IP from 7.5 instead.
Phase 8: Prove it's fixed
Run every test. Each should pass without you typing any network command. After each, check with:
nmcli device status | grep -iE 'enx|usb'     # should say: connected  Airtel-4G
ping -c3 google.com
ssh user@<jetson-ip-or-name>.local 'hostname'
[ ] Replug test: unplug the dongle, wait 10 s, plug it back in. Connected within 60 s.
[ ] Different port test: plug it into a different rear port. Connected within 60 s (proves the profile is no longer tied to a name or MAC).
[ ] Dongle power-cycle test: switch the dongle off and on (or unplug for 1 minute). Connected within 90 s.
[ ] Reboot test: sudo reboot with the dongle plugged in. Connected after login.
[ ] Cold boot test: shut down, unplug the Z440 power for 1 minute, boot. Connected after login.
[ ] Jetson test: SSH to the Jetson works after each test above.
[ ] Long-run test: leave a job running overnight, then check journalctl -u NetworkManager --since yesterday | grep -iE 'enx|usb|Airtel' for disconnects, and journalctl -t airtel-watchdog if you set up the watchdog.

Emergency fallback and rollback
Get online right now, temporarily (lasts until unplug or reboot). Try in this order:
1. sudo nmcli device connect IFACE
2. sudo dhclient -v IFACE (if dhclient is installed)
3. Static address, only if 1 and 2 fail. Use the dongle's real subnet; check its admin IP on a phone connected to its Wi-Fi (the phone's gateway in Wi-Fi details):
sudo ip link set IFACE up
sudo ip addr add 192.168.1.100/24 dev IFACE
sudo ip route add default via 192.168.1.1 dev IFACE
sudo resolvectl dns IFACE 8.8.8.8 1.1.1.1
A static address on the wrong subnet is exactly what breaks SSH to the Jetson, so double-check the first three numbers match the gateway. Undo it with sudo ip addr flush dev IFACE.
Undo everything this runbook added
sudo nmcli connection delete Airtel-4G
sudo rm -f /etc/udev/rules.d/40-airtel-modeswitch.rules /etc/udev/rules.d/50-airtel-power.rules
sudo rm -f /etc/netplan/60-airtel.yaml && sudo netplan apply
sudo systemctl disable --now airtel-watchdog.timer
sudo rm -f /etc/systemd/system/airtel-watchdog.* /usr/local/bin/airtel-watchdog.sh
sudo systemctl daemon-reload; sudo udevadm control --reload-rules
If you added usbcore.autosuspend=-1 (6.2), remove it from /etc/default/grub, then sudo update-grub. Your original state is saved in ~/dongle-debug/ from Phase 0.5.
Last resort: if nothing in this runbook works, check the dongle's own Wi-Fi on your phone. If its Wi-Fi name appears and gives internet on the phone, the dongle and SIM are fine and the fault is on the Z440's USB side; a PCIe USB card is the workaround if its ports are damaged. If the Wi-Fi name never appears on any power source, ask Airtel for a replacement.
