# Phase 7 (Build 1) Runbook — Data-Model Invariants + Map Coverage

Companion to the earlier phase runbooks. Read §1 and §4.1 before
debugging anything related to observation counts, dangling references,
or map-point culling — this build found the third and fourth instances
of a bug SHAPE Phase 6 already found once, and built a permanent tool
(`validate.py`) specifically so a fifth instance doesn't need to be
found by hand again.

Also read this if you're picking up Build 2 (the real-time iSAM2 back
end) — everything here is what it will be built on top of.

## 1. What changed, in one paragraph

Three data-model invariant bugs were found and fixed at the root:
`MapPoint.observations` was being polluted with non-keyframe frame ids
(a Phase 6 fix that over-corrected), `kf_seq` was a per-map counter that
silently invalidated point ages across a merge, and RGB-D mode never
triangulated far points at all, leaving the map with zero far-field
structure to hold onto during rotation. A new module, `validate.py`,
checks eight Atlas-wide invariants and is meant to be run constantly,
not just when something looks wrong. Running it for the first time
surfaced FOUR more bugs this phase wasn't looking for, three of them the
same underlying failure shape (a dict-based observation registry going
stale relative to what a keyframe's own array actually holds) that
Phase 6 already found once — this is now the third and fourth time this
exact shape has recurred, in different call sites. Map coverage also
improved: stratified spatial point selection, rotation-triggered
keyframe insertion, and the `emitter_on` manifest column (written since
early on, never consumed) is now actually used.

## 3. Pre-flight checklist

**3.1 — Run `validate.py` on any Atlas state you have, first, before
anything else.** This is the single most useful health check this
build introduced, and it now runs in code rather than by hand:
```python
import validate
report = validate.validate_atlas(slam.atlas)
print(report)   # empty error/warning lists = clean
n_valid, n_total, pct = validate.reference_validity_rate(slam.atlas)
print(f"{n_valid}/{n_total} = {pct:.1f}%")
```
Expect **zero errors and >99% reference validity** on any healthy run —
this project's own synthetic measurement after all Build 1 fixes landed
was 100.0% on both a plain scroll sequence and a rotation-heavy yaw
sequence. If you see errors, the printed messages name the exact
keyframe/point ids involved — that's enough to start tracing without
needing to reproduce the ablation methodology from scratch (see
PROGRESS.md's Phase 7 section for the full trace of how each of the
four newly-found bugs was isolated, as a worked example).

**3.2 — Run the full seven-phase gate before hardware.**
```bash
python3 test_phase7_gate.py
```
This internally re-runs Phases 1, 2, 3, 5, and 6's own gates (Phase 4's
gate no longer exists — see §0) and exercises all of Build 1's own
fixes directly. Budget several minutes; it processes multiple synthetic
sequences through the real `SLAMSystem` and shells out to run every
earlier phase's gate script as a subprocess.

**3.3 — Confirm the vocabulary cache exists** before running anything
that touches loop closing or relocalization (unchanged requirement from

## 4. Symptom → diagnosis → fix

### 4.1 — `validate.py` reports errors, or reference validity drops below 99%

Read the SPECIFIC error messages first — they name the exact keyframe id,
point id, and (where relevant) keypoint index involved, which is enough
to start tracing without guessing. Before assuming this is a brand-new
bug, check whether it matches one of the four failure shapes this phase
already found and fixed (all documented in detail in PROGRESS.md's Phase
7 section, with the exact tracing technique used for each):

- **`check_observations_are_keyframes` fires** ("references frame X,
  which is not a live keyframe") — look for a NEW `add_observation()`
  call site that might be running on non-keyframe frames. Grep for it:
  ```bash
  grep -n "add_observation" *.py
  ```
  Every call site should be either (a) constructing a brand-new
  MapPoint with an empty observations dict, or (b) inside `local_
  mapping.process_new_keyframe`'s reconciliation step, or (c) inside
  `fusion.py`'s two sites (which now correctly use the stale-index
  return value — see below). If you've added a new one that registers
  an ordinary TRACKED (non-keyframe) frame, that's the Phase 6 bug
  recurring in a new location.

- **`check_map_point_id_consistency` fires** ("dangling reference") —
  this is the symptom, not the cause. Trace the SPECIFIC point id's full
  lifecycle the same way PROGRESS.md's Phase 7 section does: hook
  `MapPoint.__init__`, `MapPoint.add_observation`, `Map.erase_map_point`,
  and `Map.clean_bad_points` to print whenever they touch that exact id,
  then re-run the failing scenario. The four bugs this phase found were
  all discovered exactly this way — don't guess, trace.

- **A caller re-registers an already-observing frame at a NEW keypoint
  index** — this is the general failure shape underlying THREE of the
  four bugs found this phase (see PROGRESS.md's bugs 5 and 6). `MapPoint.
  add_observation()` now RETURNS the previous keypoint index if this
  happens (`None` if it's a genuinely new observation). **Any caller
  that might legitimately re-register an existing frame_id at a
  different index MUST use this return value** to clear the OLD
  keyframe-side `map_point_ids[old_idx]` slot — see `fusion.py`'s two
  call sites for the pattern. If you add a new caller that could hit
  this (anything involving point fusion, merging, or re-matching an
  already-tracked point) and don't use the return value, you will
  silently reintroduce this bug family.

- **A one-directional matcher call produces a duplicate correspondence**
  — `Matcher.match()` and `Matcher.match_ratio()` (which wraps `cv2`'s
  `knnMatch`) both guarantee a unique QUERY index per call but make NO
  such guarantee on the TRAIN index. If you add a new call site that
  builds `frame.map_point_ids[m.queryIdx] = some_id` directly from
  matcher output, call `Matcher.dedupe_by_train_idx(matches)` on the
  result FIRST (matches are already sorted best-distance-first, so this
  keeps the best match per train index and drops worse duplicates). This
  was the actual root cause of the largest reference-validity failure
  found this phase (93.5%, should be >99%) — see PROGRESS.md bug 5 for
  the full trace, including why it existed since Phase 3 without ever
  being caught before this phase's own validator existed.

### 4.2 — Map coverage or point counts look different from Phase 1-6 baselines

Expected, and not itself a problem. Several deliberate changes affect
this: `max_new_points_per_kf` 100→300, `depth_max` 3.5m→6.0m,
`keyframe_min_displacement` 0.10m→0.25m (fewer, more spread-out
keyframes), and RGB-D mode now triangulates far points where it
previously created zero. If you have EXTERNAL baselines recorded before
this phase, don't expect them to match exactly — check `validate.py`
and `test_phase7_gate.py` instead, which were written/recalibrated
against the current behavior.

### 4.3 — A synthetic scene with a single fixed depth doesn't exercise the close/far split

Expected — `scroll_sequence()` and `yaw_sequence()` both use ONE depth
for the whole scene, so every point is either all-close or all-far and
the split can't be meaningfully tested with them. Use `synthetic.
two_depth_scroll_sequence()` instead (new this phase) — it composites a
near plane and a far plane in the same frame specifically for this.

### 4.4 — Rotation-triggered keyframes seem to fire too often or too rarely

`keyframe_min_rotation_deg` (default 15°) is a straightforward
threshold against `imu.log_so3`'s angle between the current frame's pose
and the last keyframe's — there's no smoothing or hysteresis. If real
hardware shows this firing on ordinary head-turn jitter, raise it; if it
never fires during genuine rotation, lower it and re-check with
`test_phase7_gate.py`'s Test 9 pattern (a direct unit test against
`Tracking.needs_new_keyframe`, no full pipeline needed) before touching
anything else.

### 4.5 — `run_dataset.py --ir` recordings behave differently than before

Expected — tracking now uses ONLY emitter-off (clean) frames and borrows
depth from the nearest emitter-on neighbor, roughly halving the
EFFECTIVE tracked frame rate for `--ir` recordings specifically (plain
RGB recordings, with no `emitter_on` manifest column, are completely
unaffected). This was previously recorded but silently ignored; the
emitter's dot pattern was going straight into the extractor on every
frame. If this regresses tracking quality on a specific recording,
check first whether that recording actually alternates the emitter (has
a real `emitter_on` column with both True/False values) — a recording
made without `--ir` won't trigger this code path at all.

## 5. Testing order

1. `validate.py` on a fresh, short recording (§3.1) — confirms the core
  fixes are in place before testing anything more elaborate.
2. Full `test_phase7_gate.py` suite (§3.2).
3. `two_depth_scroll_sequence()` (§4.3) if you're specifically verifying
  the close/far split rather than trusting the gate suite's own check.
4. A real facility recording, `run_dataset.py`, checking `validate.py`'s
  reference-validity percentage stays >99% throughout — not just at the
  end, since the four bugs found this phase all manifested as gradual
  degradation, not an immediate crash.

## 6. What "success" looks like for this build

1. `validate.py` reads zero errors and >99% reference validity on real
  hardware footage, not just synthetic tests.
2. A rotation-heavy real segment (turning to look down a corridor, the
  original failure mode from the very first forensic pass on this
  project) shows tracked point count holding up better than Phase 1-6
  baselines, because far points now survive rotation where they
  previously didn't exist at all.
3. No unexplained new fragmentation compared to Phase 5/6 baselines —
  the config changes (larger keyframe spacing, more points per keyframe)
  should if anything reduce map-lifecycle churn, not increase it.
4. If you recorded with `--ir`, `run_dataset.py`'s output shows the
  `[emitter]` log line reporting a real on/off frame split, not silence
  (silence means the manifest doesn't have the column at all — check
  the recording was actually made with `--ir`).
